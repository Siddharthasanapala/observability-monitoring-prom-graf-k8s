1. Executive Summary

This report documents the design, build, and validation of a production-shaped observability platform on Kubernetes, covering the three pillars of observability — metrics, logs, and distributed traces — together with dashboards, automated alerting, role-based access control, network segmentation, and a real instrumented workload used to prove the pipeline end-to-end rather than with synthetic test data.

The platform was built hands-on on a locally provisioned Kubernetes cluster (Minikube, sized and configured to mirror a real node pool) and is 100% managed through ArgoCD, meaning the Git commit history of this repository is the authoritative change history of the cluster. No component was ever deployed by a one-off manual command that isn't also reproducible from source control. The same design has been packaged as two cloud-native Helm charts — one for Google Kubernetes Engine (GKE), one for Amazon EKS — so the identical architecture can be installed on either managed cloud platform with only cloud-specific values (storage class, ingress controller, identity federation) changed.

2. Objectives and Scope

The initiative set out to answer a concrete engineering question: what does an enterprise-grade observability platform on Kubernetes actually require, beyond installing Prometheus and Grafana and calling it done? The scope was defined as:

  1. Full observability coverage — not metrics alone, but metrics, logs, and traces working together, with a real workload proving correlation between them.
  2. GitOps as the operating model, not an add-on — every piece of cluster state, from namespaces to alert rules, deployed and changed only through version-controlled declarations, reconciled automatically by ArgoCD.
  3. Enterprise baseline hygiene — multi-tenant namespace isolation, least-privilege RBAC, network segmentation, and pod security hardening, applied from the start rather than retrofitted.
  4. Cloud portability — the same architecture packaged so it can be installed on GKE or EKS without redesign, only cloud-specific configuration substitution.
  5. Provable correctness — an automated validation gate that checks the platform end-to-end, so "it's done" is a test result, not an opinion.

Out of scope for this phase: production-grade identity federation (OIDC/IdP integration is designed for but not wired to a real identity provider), long-term object storage backends for Loki/Tempo (designed as an opt-in overlay, not enabled by default), and a CI/CD pipeline for this repository itself. These are called out explicitly in Section 12.

3.3 Key Architectural Decisions

Everything through ArgoCD, with exactly one exception

The only manifests ever applied directly with kubectl are ArgoCD's own installation and a single root Application that bootstraps the App-of-Apps pattern. Every other object in the cluster — namespaces, RBAC, NetworkPolicies, the entire metrics/logs/traces stack, dashboards, alert rules, and the sample application — is a child Application reconciled automatically from this repository. This is elaborated in Section 5.

Namespace-per-concern multi-tenancy

Four tenant namespaces — observability, logging, tracing, demo-app — each carry their own ResourceQuota, LimitRange, restricted Pod Security Standard labels, and default-deny NetworkPolicy with explicit allow rules. kube-system deliberately opts out of the restricted policy because it hosts the two DaemonSets (node-exporter, Promtail) that require genuine host access — a constraint identified and documented before either component was deployed, not discovered as a surprise mid-build.

Everything version-pinned, nothing left floating

The Kubernetes version, every Helm chart version, and every container image tag are pinned to an exact version — never latest or a floating channel. The sample application goes further: its deployment references an immutable commit-SHA image tag, so "what is running in the cluster" always maps to one exact, inspectable source commit.

A CNI that actually enforces policy

Minikube's default CNI does not enforce NetworkPolicy at all — this was proven with a live test where traffic crossed a default-deny policy that should have blocked it, and didn't. The cluster was switched to Calico specifically so NetworkPolicy has real teeth, matching how GKE (Dataplane V2) and EKS (Calico / VPC CNI policy support) enforce network policy in production.

4.3 Why Pinned Dependencies Matter Here

Every chart version above is locked in both the GitOps Application manifests and the two distributable Helm charts' Chart.lock files. This is a deliberate governance choice: a chart maintainer publishing a new default (as happened during this build, when a newer OpenTelemetry Collector chart version silently dropped its default container image) cannot change what is running in this platform without a reviewed, version-controlled commit. For an enterprise environment, this converts "a third-party dependency changed under us" from a production incident into a routine, reviewable pull request.

5. GitOps Delivery Model — ArgoCD

5.1 Why GitOps

Traditional Kubernetes operations rely on operators running kubectl apply or helm install commands directly against a cluster. This is fast to start with and difficult to govern at scale: there is no single place to see what changed, when, why, or who approved it, and the live cluster state can silently drift from whatever was last documented. GitOps inverts this relationship — the cluster continuously converges toward whatever is declared in a Git repository, and a controller (here, ArgoCD) is responsible for making that true, not a human running commands.

5.2 The App-of-Apps Pattern

This platform uses ArgoCD's "App-of-Apps" pattern: a single root Application (bootstrap/root-app.yaml) watches one directory in this repository (argocd-apps/) and turns every Application manifest found there into a live, independently-reconciled child Application. Adding a new platform component is therefore: write the desired-state manifests, drop one Application file into argocd-apps/, commit, and push — ArgoCD does the rest, with no new tooling and no change to the bootstrap process.

5.4 Self-Healing in Practice

Every Application in this platform runs with automated: {prune: true, selfHeal: true}. In practice this means any direct kubectl or helm edit made against the live cluster — including edits made for urgent troubleshooting — is treated as drift and reverted to match the last commit pushed to Git, typically within three to five seconds. This was observed repeatedly during hands-on development and is correct GitOps behavior, not a defect: Git is authoritative by design. The documented technique for safely validating a fix live before committing it is to temporarily pause that one Application's sync policy (argocd app set <name> --sync-policy none), verify the fix, push it, then restore automated sync. This same behavior is what makes the platform resilient against configuration drift in production: a well-intentioned but undocumented manual fix cannot quietly become permanent, hidden state.

Governance benefit: because RBAC in this platform deliberately excludes namespace-admin personas from editing RBAC, ResourceQuota, LimitRange, and NetworkPolicy objects directly (Section 7), and those same objects are ArgoCD-managed with self-heal, governance configuration in this cluster can only change through a reviewed Git commit — not through elevated runtime access, and not by accident.

6. Monitoring and Observability Configuration

The platform implements all three observability pillars — metrics, logs, and traces — as independently scalable components that are unified in a single Grafana pane, and proves the unification with a real request rather than a synthetic demonstration.

6.1 Metrics — Prometheus

Deployed via the kube-prometheus-stack chart with Prometheus running 2 replicas for availability, backed by persistent storage. Metrics sources include:

  • Kubernetes control-plane and workload metrics via kube-state-metrics
  • Node-level host metrics via node-exporter (DaemonSet, one per node)
  • Application metrics scraped directly from the sample workload's /metrics endpoint — no push gateway in the path
  • Prometheus Operator CRDs (ServiceMonitor, PrometheusRule) used throughout, so scrape targets and alert rules are themselves Kubernetes objects managed by ArgoCD

At last validation, all active scrape targets reported healthy (21/21 up). Three control-plane targets (kube-scheduler, kube-controller-manager, kube-etcd) are intentionally excluded on this Minikube reference environment, as Minikube hardcodes those static pods to bind to localhost only — a Minikube-specific limitation, not a design gap; on GKE/EKS these are cloud-managed and exposed differently.

6.2 Visualization — Grafana

Grafana is provisioned with persistent storage and pre-wired datasources for Prometheus, Loki, and Tempo, so an operator can pivot between metrics, logs, and traces without manually configuring a single connection. Dashboards are defined as code — raw dashboard JSON committed to this repository, wrapped into a ConfigMap via Kustomize, and picked up automatically by Grafana's sidecar watcher. A platform-overview dashboard and a sample-application dashboard are included; the platform overview generalizes to any workload, while the sample-app dashboard demonstrates request-rate, error-rate, and latency panels backed by real traffic.

6.3 Logging — Loki and Promtail

Loki runs in SingleBinary mode — the appropriate topology at this scale, avoiding the operational overhead of a multi-component read/write/backend split that would only add complexity without a corresponding benefit. Promtail runs as a DaemonSet in kube-system (it requires host path access incompatible with the platform's restricted namespaces) and tails every container's stdout across the entire cluster. At last validation, Loki held ingested log streams from all active application and platform namespaces — every namespace, confirmed via Loki's label API, not assumed from configuration alone.

6.4 Distributed Tracing — OpenTelemetry and Tempo

Application traces are exported over OTLP to a dedicated OpenTelemetry Collector, which forwards them to Tempo (single-binary mode, persistent storage). A dedicated collector sits in front of Tempo by design — even though Tempo itself accepts OTLP directly — so instrumented applications depend on a vendor-neutral ingestion point rather than being coupled to Tempo specifically, preserving the option to redirect traces to a different backend later without touching application code.

6.5 Alerting — Alertmanager and SLO Rules

Alertmanager runs a 3-replica cluster — deliberately an odd number for real gossip-protocol quorum, since two replicas provide no genuine high-availability advantage over one. Alert rules are authored as PrometheusRule custom resources, version-controlled alongside everything else, and organized into three groups:

  • Node health — high CPU, high memory, node-not-ready conditions
  • Pod crash-loop detection — cluster-wide, workload-agnostic
  • Application SLO — a burn-rate error-rate alert pattern for the sample application, intentionally a simplified single-window model rather than the full multi-window Google SRE workbook approach, documented as such so the trade-off is explicit rather than implied.

These rules were validated with two real fired-and-resolved alerts, not simulated conditions: a deliberately induced failing endpoint drove the SLO error-rate alert from pending to firing to resolved, confirmed live in Alertmanager; and the crash-loop alert correctly caught a genuine tracing-backend memory issue during load testing, which was then diagnosed and fixed — evidence the alerting pipeline detects real problems, not only lab conditions.

6.6 Cross-Pillar Correlation

The platform's central observability claim — that metrics, logs, and traces work together, not merely alongside each other — was proven directly: a single real request's trace ID was located in both Tempo (as the actual multi-span distributed trace) and Loki (as a structured log line carrying the identical trace ID field), while the corresponding business metric incremented correctly in Prometheus for the same request. One trace ID, one real request, present and correlated across all three pillars simultaneously.

6.7 The Instrumented Reference Workload

An ASP.NET Core (.NET 10) sample application was purpose-built to prove the pipeline rather than generate synthetic load. A single API call (GET /api/orders/{id}/enriched) triggers a genuine internal HTTP call to a second endpoint, producing a real three-span distributed trace rather than a single isolated span. The application exports:

  • Metrics — ASP.NET Core auto-instrumentation plus custom business-event counters, scraped directly by Prometheus
  • Traces — OTLP export to the in-cluster collector, endpoint configured via environment variable, never hardcoded
  • Logs — structured JSON to stdout, enriched with the active trace and span ID, tailed by the same cluster-wide Promtail pipeline as every other workload — deliberately not a second, parallel logging path

7. Security and Governance

7.1 Role-Based Access Control

Two personas are defined per tenant namespace, bound to Kubernetes Groups rather than individual ServiceAccounts, so they can be wired directly into a real identity provider's group claims later without any change to these manifests:

  • sre-viewer — read-only access, explicitly cannot read Secrets
  • observability-admin — full CRUD on workload resources, but deliberately excluded from RBAC objects, ResourceQuota, LimitRange, and NetworkPolicy — governance configuration remains GitOps-only, not self-service even for a namespace administrator

7.2 Network Segmentation

Every tenant namespace enforces a default-deny-all NetworkPolicy with explicit, narrowly scoped allow rules layered on top — traffic is denied by default and permitted only where a documented need exists (for example, Grafana querying Prometheus, or Promtail pushing logs into Loki from a different namespace). This is enforced at the CNI layer via Calico, confirmed with a live positive-and-negative connectivity test rather than assumed from the policy YAML alone.

7.3 Pod Security Standards

The restricted Pod Security Standard is enforced via namespace labels on all four tenant namespaces — no privilege escalation, no root containers, mandatory seccomp profiles, dropped Linux capabilities. Components that structurally require host-level access (node-exporter, Promtail) are namespaced into kube-system instead of weakening the tenant namespaces' policy, a conflict identified and documented before either component was deployed.

7.4 Certificate Management

cert-manager is deployed with a self-signed ClusterIssuer on the Minikube reference environment, proving the certificate-issuance pattern end-to-end. The GKE and EKS documentation (Section 9) specifies the cloud-managed equivalents — Google Certificate Manager with Workload Identity, and AWS Certificate Manager with IRSA — as direct drop-in replacements for production use.

A clean run reports all checks passing before any downstream documentation or packaging phase is considered complete.

11. Operational Lessons and Runbook

Self-heal reverts unpushed live edits — by design

Any direct cluster edit not yet committed to Git is treated as drift and reverted, typically within seconds. This is the correct, intended GitOps behavior, and the documented workaround for validating a fix live before committing is to temporarily pause the specific Application's sync policy, never to disable self-heal platform-wide.

Grafana's admin credential can desync from its own Secret once persisted

The admin password environment variable only seeds a brand-new database on first boot; once persistent storage is enabled, later credential rotations do not automatically propagate to the already-existing admin account. The durable fix is resetting the password through Grafana's own CLI inside the running pod, which updates the persisted database without disturbing dashboards or datasources.

Third-party Helm chart defaults are a starting point, not a compliance guarantee

Every Helm-deployed component in this platform required at least one real, live-deployment correction that reading the chart's documentation alone would not have surfaced — a missing security field, a resource default colliding with namespace limits, a value nested at the wrong key path in an upstream chart's schema (found during this engagement's own live cross-check and corrected). The pattern that reliably catches these: inspect a chart's actual rendered defaults before writing values, deploy against a real cluster, read the actual error, fix it, and re-verify — rather than trusting documentation or a clean template render alone.

Reproducibility from a clean slate

The entire platform — cluster, GitOps controller, and every managed component — can be rebuilt unattended from a single script following a Minikube teardown, provided the Git repository already holds the desired state. This was a deliberate design goal, not an afterthought: infrastructure that can only be recreated by someone who remembers the original manual steps is not truly GitOps-managed.

12. Conclusion and Recommendations

This engagement delivered a working, provably correlated observability platform — not a proof-of-concept dashboard, but a system validated with real traffic, real fired alerts, and a real traced request — governed entirely through GitOps, hardened with enterprise-baseline security controls, and packaged for deployment on two major public clouds without architectural change. The 26-check automated validation gate and the reproducible setup script together mean this platform's correctness is a repeatable test result, not a point-in-time claim.

Recommended Next Steps for Production Adoption

  1. Identity federation — connect the existing RBAC Group bindings to a real identity provider (OIDC/SAML), which requires no change to the RBAC manifests themselves, only IdP configuration.
  2. Durable object storage for logs and traces — enable the already-built GCS/S3 overlay for Loki and Tempo before retention needs exceed local persistent volume capacity.
  3. Cloud-managed certificates — replace the self-signed issuer with Google Certificate Manager or AWS Certificate Manager plus Workload Identity/IRSA, both already documented as direct replacements.
  4. Continuous integration for this repository — add automated helm lint/schema validation on every pull request, extending the manual validation already performed to a standing CI gate.
  5. Formal alert routing — wire Alertmanager's receivers to real paging/notification channels; the alert rules and severities are already defined and proven to fire correctly.
